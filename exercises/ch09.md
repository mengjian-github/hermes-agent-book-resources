# 第9章：委派与看板

对应书稿 9.11，共 7 题。题干为摘要；按书中原顺序编号。核查日期：2026-09-18。共同前提与验证记录见 [练习说明](README.md)。

## 9.11-1 拆分三个独立研究任务

前提：给三个子任务相同截止日期、来源范围和输出格式。

参考步骤：任务A goal=列本地安装前提，context=仅官方安装页，输出要求/来源/缺口；B goal=列定时日报路径，context=仅官方Cron页，输出步骤/来源/风险；C goal=列Telegram接入条件，context=仅官方Telegram页，输出条件/来源/限制。主 Agent 汇总交叉依赖。

验收：三个任务不等待彼此产物，各自有证据；汇总时统一版本和术语。

排查与边界：不能让三者同时编辑同一文件，也不能用“自行研究”代替具体 context。

## 9.11-2 代码审查工具选择

前提：先决定审查是否真的需联网或对外发送结果。

参考步骤：在父会话选择文件读取/必要验证能力，检查 `/tools list`；无联网需求就不加 web，无通知需求就不开放消息发送。delegate_task 只传实际支持的 goal/context 等参数。

验收：说明 send_message 是工具名，toolsets 不是 delegate_task 参数；检查子任务继承后的可见能力。

排查与边界：file 工具集可能包含写操作，不等同只读；提示约束只是行为要求。

## 9.11-3 只读委派

前提：在临时副本或只读挂载内审查，必要工具不能写目标文件。

参考步骤：先保存文件哈希/git status；委派 goal=仅指出认证风险，context=目录与不修改要求；完成后重新比对哈希与 diff，检查轨迹。

验收：无代码修改且给出证据；若仅靠提示词，明确称为行为约束，不声称强隔离。

排查与边界：有终端或代码执行权限时仍可能写文件，需要操作系统边界保障。

## 9.11-4 delegate_task 与 execute_code

前提：合成数据 [{team:A,hours:2},{team:B,hours:3},{team:A,hours:4}]。

参考步骤：方案1：代码按 team 求和，结果 A=6/B=3；方案2：委派同一统计任务，要求给算法和验算。比较调用数、耗时与确定性。语义研究适合委派，简单求和宜确定性代码。

验收：两者结果相同，记录真实耗时，不编造性能比例。

排查与边界：execute_code 的可用 API 取决于环境；不能假设里面可以任意 import 或调用未暴露工具。

## 9.11-5 观察 /agents

前提：在支持委派的父会话启动任务。

参考步骤：任务运行时 `/agents`，记录 ID、状态、目标，完成后收集每项摘要与证据，主 Agent 再核验。非异步环境记录同步完成而非强行制造后台状态。

验收：最终交付含真实产物；排队/运行中不能写成已完成。

排查与边界：后台可靠结果投递不等于进程崩溃后能恢复执行。

## 9.11-6 Kanban 状态流转

前提：仅测试板，避免活跃调度器消费练习卡。

参考步骤：照[看板操作手册](../examples/ch09-multi-agent-todo-api/kanban-webhook.md)新建板和卡，comment、block、补证据、unblock，逐次 show。

验收：记录 ready→blocked→ready 和原因；无依赖才期待直接 ready，最后归档练习卡。

排查与边界：Todo API 是另一个项目，不能拿其 CRUD 代替 Hermes Kanban 操作。

## 9.11-7 Webhook PR 审查

前提：本题交付方案与测试用例，不要求暴露公网服务。

参考步骤：采用[完整设计](../examples/ch09-multi-agent-todo-api/kanban-webhook.md)：验证签名→仓库/事件白名单→repo/PR/SHA幂等→三角色只读→汇总等待→检查SHA→经授权发布。

验收：覆盖重复事件、新提交、角色失败、无发布权限；附输入样本与状态记录。

排查与边界：PR正文是不可信材料，不能拼成 shell 命令；不自动 approve/merge。

依据：[本章官方参考](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation)。具体命令以已安装版本帮助为准；题干需修改处另见 [书稿勘误](../docs/book-errata-2026-09-18.md)。
